# Working on demo-media-library

Read README.md, docs/product-brief.md, docs/decisions.md,
docs/baseline-spec.md, docs/implementation-brief.md, and docs/acceptance.md first.
Read docs/exercises.md to understand what stays outside the baseline.

## Assignment and authority

Build the agreed basic app as a reusable starting point for later learning and
ExecDesk dogfooding. This pack is context, not evidence that proposals are approved
or features exist. The current user message determines the authorized engagement.

- Inspect the checkout and decision register before coding. Confirm the catalog
  interpretation, baseline, and stack; do not silently assume media file storage.
- Present remaining consequential choices in a compact recommendation with
  alternatives. Ask Gabriel before implementing dependent work. Continue useful
  independent preparation while waiting; silence is not approval.
- Respect accepted choices. Do not reopen them without a concrete blocker.
- Once implementation and required decisions are authorized, proceed through
  routine edits, documentation, verification, and review preparation without
  repeated confirmation. Stop for new consequential product, UX/design,
  architecture, dependency, privacy, data, or scope choices.
- Use focused, readable files. Avoid giant components/controllers and unnecessary
  infrastructure. Use proportionate checks rather than exhaustive test matrices.

## Boundaries

- Work only in this repository. No changes to ExecDesk or sibling demo systems.
- Optional exercises are not assigned work. Do not implement or file them as issues.
- Final acceptance and consequential decisions remain Gabriel's unless delegated.
- No commits, pushes, merges, tags, external issues/PRs, deployment, publishing,
  or visibility changes without explicit authority for this project.
- No paid services, credential acquisition, scraping, or external runtime
  integrations without authorization. Use original synthetic catalog fixtures.
- Do not download real covers or media. Placeholder visuals, if agreed, can be
  locally authored; do not introduce an asset pipeline just for decoration.
- Do not discard unrelated edits or reset existing data as incidental cleanup.

## Handoff

Report what works, verified run/reset instructions, checks actually performed,
known limitations, decisions made during work, and anything requiring review.
Leave a reviewable working tree. Implementation complete, human accepted, and
committed/pushed are separate states.

## Preserve the baseline during exercises

Before changing files for an exercise, inspect the current branch and working tree.
Use a separate exercise branch; if the checkout is on main, create or switch to an
exercise branch before editing. Preserve unrelated changes. Do not merge exercise
solutions into main automatically. A completed exercise may remain uncommitted or
unmerged. Baseline maintenance and promotion of exercise work require explicit
authorization; commit/push authority is still governed by the boundaries above.
